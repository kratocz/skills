# AGENTS.md

Guidance for agents (and humans) maintaining this repository.

## What this is

A collection of portable [Agent Skills](https://agentskills.io/) — one directory per skill under `skills/<name>/` with a `SKILL.md` entry point — installable into 70+ agent harnesses via `npx skills add kratocz/skills`. Claude-Code-specific plugins (lifecycle hooks, statusline) live separately in [kratocz/claude-plugins](https://github.com/kratocz/claude-plugins); do not add hook-dependent skills here.

## Distribution model (verified 2026-08-01)

- `npx skills add` installs a **physical copy** of each skill into `~/.agents/skills/` (the "universal" directory) and creates per-agent symlinks to it (e.g. `~/.claude/skills/<name> → ../../.agents/skills/<name>`). Local-path installs are not tracked by `skills update` — refresh them by re-running the add.
- Directory reality on tested harnesses: `~/.agents/skills/` is read by Codex, Copilot CLI, Gemini CLI, opencode, Antigravity CLI (interactive sessions), and Claude Code (with a delayed index). `~/.claude/skills/` is picked up by Claude Code instantly, including hot-reload into running sessions.
- Antigravity's `agy -p` (non-interactive print mode) does not load skills at all — never use it to test skill visibility; test in an interactive session.
- Known upstream gap in the skills CLI: `-g -a antigravity-cli` installs only into `~/.agents/skills/` and never into `~/.gemini/antigravity-cli/skills/`, despite the CLI's own agent map listing that global path. It works in practice only because Antigravity reads `~/.agents/skills/`. Do not open an upstream issue for it — that is a deliberate decision, not an oversight.
- The maintainer's machines use **live symlinks** from `~/.agents/skills/<name>` straight into a working clone, so edits apply without reinstalling (`~/.claude/skills/<name>` is the CLI's own symlink to `~/.agents/skills/<name>` and resolves through). **The skills CLI does not create these — `npx skills add` always writes physical copies**, so a plain `add` silently reverts the setup, and it has to be re-established afterwards:
  ```bash
  CLONE=$(pwd)   # a working clone
  for n in $(ls "$CLONE/skills"); do
    [ -f "$CLONE/skills/$n/SKILL.md" ] || continue
    rm -rf ~/.agents/skills/"$n" && ln -s "$CLONE/skills/$n" ~/.agents/skills/"$n"
  done
  ```
  Before replacing anything under `~/.agents/skills/`, confirm each target is this repo's — its `SKILL.md` exists and its frontmatter `name` equals the directory name — and leave everything else alone; that directory also holds skills from other sources. Verified 2026-08-26: this claim had drifted from reality, all 27 skills sat as copies from the previous day, and a `/work-reconcile` run made to test a fix silently executed the **old** version instead. Trusting an installed skill to match the clone is the failure mode; check `version:` on both sides when a test result looks like the edit never happened.

## Authoring rules

- **Stay harness-neutral.** Describe actions, not tools ("read the file", not "use the Read tool"), and never assume one specific harness is the runtime — harnesses may appear as examples. This covers interactive prompts too: write "ask the user to choose: A / B / C" rather than naming a harness's question tool. The wording carries the intent either way, and a harness that has a structured picker will still reach for it. Frontmatter extras (`allowed-tools`, `argument-hint`, `version`) are Claude-specific; keeping them is fine.
- **`argument-hint` must be a quoted string.** It is the one frontmatter extra that is *not* harmlessly ignored elsewhere: the skills CLI parses the YAML, so a bare `[--since X] [--until Y]` is read as a flow sequence. Four skills in this collection failed to parse at all and were silently skipped by `npx skills add` — never installable via the CLI — while Claude Code tolerated every variant, which is why nothing looked broken locally. Quote it, and check the value survives `npx skills add . --list`.
- **Diagnostic thresholds are measured, not reasoned about.** When a skill tells an agent "value X means the system is broken", run the query against a machine known to be healthy before writing X down, and check what the query actually counts. A threshold added here on 2026-08-10 compared `mdfind -count -onlyin /Applications "kMDItemFSSize > 0"` against `find -maxdepth 4 | wc -l` and declared a working Spotlight index dead — the predicate skips directories, so it never counted a single `.app` bundle, and the two numbers were never comparable in the first place.
- **Destructive steps delete only what the skill owns.** When a skill tells an agent to remove files, symlinks or cache entries as cleanup, it has to establish ownership first — resolve a symlink with `readlink` and confirm the target points inside the tree the skill itself created (including that tree's former names) — and report anything else as `left untouched: <link> -> <target>` instead of deleting it. A broken link is usually temporary (a renamed repo, an unmounted disk) and the link is itself the record of where it pointed. This governs cleanup only; it does not apply where removal *is* the documented repair, as in `launchpad-fix` recreating the Spotlight store.
- **Paths.** Session transcripts and project memory live under `<harness-home>/projects/<slug>/`, where `<harness-home>` is `~/.claude` (Claude Code) or `~/.gemini/antigravity-cli` (Antigravity CLI) — use the first that exists. Skill state/config deliberately stays under `~/.claude/plugins/<name>/` (historical location; it is just a path, readable from any harness — no migration).
- **Names must be unique across the flat collection** and the directory name must equal the frontmatter `name`. Suites use prefixes (`tracker-*`, `work-*`).
- **Trigger phrases must discriminate, not just describe.** A `description` competes with every other description in the collection, so a phrase that reads naturally for two skills routes to whichever the model picks first — silently, and the user sees only the wrong result. This bites hardest between suites that share a domain: until 2026-08-11 `tracker-stop` advertised "end session", "I'm done" and "finished working", every one of which also means "the working day is over" (`work-end`), and `tracker-backfill` and `work-reconcile` both offered to fill in missing Toggl time with nothing saying which one covers the current session and which a past period. When two skills touch the same domain, give each description its own scope in its own words plus one clause naming its counterpart ("Not the end-of-day summary — that is `work-end`"). Drop any phrase you cannot assign to exactly one skill; an agent that has to ask beats one that guesses.
- **A mistyped command name cannot be fixed from a description.** Harnesses that expose skills as slash commands resolve the name locally: an unknown `/foo` is rejected before the turn starts and never reaches the model, so listing `"/foo"` among another skill's trigger phrases does nothing at all. Verified 2026-08-11 — a command the user reported typing by mistake "every now and then" appears in no session transcript. Fix a habitual typo where the name is resolved, in a personal command alias in the user's own config, never by adding an alias skill to this collection: every skill here costs description context in every session, for every user. And first establish which skill the user actually meant — an alias pointing at the plausible-but-wrong one converts a visible error into a silent wrong action.
- **Czech strings are functional, not accidental.** Trigger phrases in descriptions and user-facing message templates exist because the primary user works in Czech; skills phrase runtime output in the configured language. Do not "translate them away". Documentation prose, on the other hand, is English. Three rules keep that from stranding an English user, all three added 2026-08-26 after an audit found the whole `work-*` suite failing them:
  - **Say once that the quotes are examples.** Right where the skill reads `config.language`, state that every quoted user-facing string below is an example written in `cs`. Without that sentence a table of labels reads as a canonical string spec and gets emitted verbatim — the risk is highest exactly where the strings are most table-like (`work-reconcile`'s origin labels, its approval menu). Where an option is referred to again later, refer to it by its function (**all**, **skip**), never by its Czech string, or the reference re-canonises it.
  - **Anything that fires before the config is read carries both languages inline**, as `"<czech>" / "<english>"`. A missing-config or missing-snapshot error has no configured language to fall back on, so "phrase it in the configured language" is unactionable there and the literal wins. This is the one place bilingual text is correct rather than lazy.
  - **A setup skill asks the language before any other question**, and defaults to `en` when nothing is detectable. `work-setup` asked it in step 6 while talking to the user from step 1, so a fresh English user got five Czech steps first.
- **Config defaults must not be localized.** Message templates are rendered per user; default *values* are not. `work-reconcile` shipped `calendar.exclude_keywords=["oběd","lunch","dovolená"]`, so an English user's `Holiday`/`PTO` blocks were reconstructed as billable work and written to their timesheet. A localized default is a data bug, not a cosmetic one — cover every language the skill claims to support, and remember the match is a plain substring test, where a short token (`pto`, `off`) eats unrelated events.
- **A skill is verified by running it, and not by its author.** Reading a skill proves only that it reads well. Five `/work-reconcile` runs on 2026-08-26 each surfaced defects the previous ones had not, and the two most damaging — a coverage diff broken hours earlier, and a matching rule that contradicted its own worked example — were found only by a run in a *clean* context. Two things follow, and neither is optional for a skill that writes anywhere:
  - **Run it outside your own context.** An author re-reading their own text supplies the intent the text is missing. Dispatch a fresh-context agent, give it a neutral task rather than a hypothesis to confirm, and ask for verbatim output. Treat what comes back as claims to check, not findings to act on — one such report named a broken `awk` line that was in fact correct in the file.
  - **Extract every embedded snippet and execute it against real data.** Prose can be reviewed; code cannot. `d.get('content')` for a field actually named `aiTitle`, and `date -u -j -f` silently parsing local wall-clock as UTC, both read as obviously right and were both wrong — one blanked every row's description, the other shifted the window by the zone offset.
- **Removing a default is a change to every consumer downstream.** Dropping `work-reconcile`'s project fallback made `project=null` the normal case, and step 7 — which bucketed its busy map by `(project, day)` — then compared those blocks against an empty bucket, so nothing could ever mask them and a window already holding 33.3 h proposed 61.6 h more. Before removing a default, find every step that reads the field and check what it does with the empty value. The converse is the reason to remove it anyway: **a skill that writes into a system of record must not invent attribution.** No match means ask; a configured id meant for starting a timer is not an answer to where reconstructed time belongs.
- **A subagent near a writable system loses the credential path, not just the permission.** Telling an agent "do not write" is a request; removing what it would need in order to write is a property. When dispatching one at a skill that posts to a tracker, deny it the file holding the API key rather than only forbidding the call — and confirm afterwards from the target's own state (entry count and highest id before and after) instead of trusting the report that says nothing happened.
- **kodex** is a regular skill with an **always-on pointer**: one line in the user's instructions file makes agents load it before non-trivial work; `rules/kodex.md` is that line for Antigravity's rules mechanism, with the Czech wording of the same line in `rules/kodex-cs.md` (README offers both). The English text in `SKILL.md` is canonical; the Czech original lives in `references/kodex-cs.md`. That is **four** copies of the same instruction — the two pointer lines and the two codex bodies — and they have to move together.
- Bundled assets (`scripts/`, `references/`, templates) belong inside the skill's directory and are referenced by paths relative to it.

## Dev loop

Edit in a working clone. Symlinked installs (above) see changes immediately; copy installs refresh with `npx skills add . -g -y --all` — which also flattens any symlinks back into copies, so re-run the symlink loop after it. Verify discovery with `npx skills add . --list` (every skill must appear). When adding a skill, also add a row to the README table.

**Changelog.** `CHANGELOG.md` is date-grouped and scope-prefixed (skill name, or `repo` for collection-wide changes). Every `feat`/`fix` commit — and any other change that alters an installed skill's behavior or config contract — adds a line under today's date in the same push; typo/refactor/chore noise stays out. There are no repo-level versions or tags; the complete per-skill history remains `git log -- skills/<name>/`.

**Skill versions.** Some skills carry a frontmatter `version`, inherited from their Claude-plugin origin; it is optional, ignored outside Claude Code, and never added to a skill that lacks it. When a skill that has one changes behavior, bump it — patch for a fix, minor for a feature — and name the resulting version in parentheses at the end of its CHANGELOG line (`… (v1.6.1)`). Skills without the field get an unversioned line.
