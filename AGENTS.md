# AGENTS.md

Guidance for agents (and humans) maintaining this repository.

## What this is

A collection of portable [Agent Skills](https://agentskills.io/) — one directory per skill under `skills/<name>/` with a `SKILL.md` entry point — installable into 70+ agent harnesses via `npx skills add kratocz/skills`. Claude-Code-specific plugins (lifecycle hooks, statusline) live separately in [kratocz/claude-plugins](https://github.com/kratocz/claude-plugins); do not add hook-dependent skills here.

## Distribution model (verified 2026-08-01)

- `npx skills add` installs a **physical copy** of each skill into `~/.agents/skills/` (the "universal" directory) and creates per-agent symlinks to it (e.g. `~/.claude/skills/<name> → ../../.agents/skills/<name>`). Local-path installs are not tracked by `skills update` — refresh them by re-running the add.
- Directory reality on tested harnesses: `~/.agents/skills/` is read by Codex, Copilot CLI, Gemini CLI, opencode, Antigravity CLI (interactive sessions), and Claude Code (with a delayed index). `~/.claude/skills/` is picked up by Claude Code instantly, including hot-reload into running sessions.
- Antigravity's `agy -p` (non-interactive print mode) does not load skills at all — never use it to test skill visibility; test in an interactive session.
- Known upstream gap in the skills CLI: `-g -a antigravity-cli` installs only into `~/.agents/skills/` and never into `~/.gemini/antigravity-cli/skills/`, despite the CLI's own agent map listing that global path. It works in practice only because Antigravity reads `~/.agents/skills/`. Do not open an upstream issue for it — that is a deliberate decision, not an oversight.
- The maintainer's machines use **live symlinks** from `~/.agents/skills/` and `~/.claude/skills/` straight into a working clone, so edits apply without reinstalling.

## Authoring rules

- **Stay harness-neutral.** Describe actions, not tools ("read the file", not "use the Read tool"), and never assume one specific harness is the runtime — harnesses may appear as examples. This covers interactive prompts too: write "ask the user to choose: A / B / C" rather than naming a harness's question tool. The wording carries the intent either way, and a harness that has a structured picker will still reach for it. Frontmatter extras (`allowed-tools`, `argument-hint`, `version`) are Claude-specific and ignored elsewhere; keeping them is fine.
- **Diagnostic thresholds are measured, not reasoned about.** When a skill tells an agent "value X means the system is broken", run the query against a machine known to be healthy before writing X down, and check what the query actually counts. A threshold added here on 2026-08-10 compared `mdfind -count -onlyin /Applications "kMDItemFSSize > 0"` against `find -maxdepth 4 | wc -l` and declared a working Spotlight index dead — the predicate skips directories, so it never counted a single `.app` bundle, and the two numbers were never comparable in the first place.
- **Destructive steps delete only what the skill owns.** When a skill tells an agent to remove files, symlinks or cache entries as cleanup, it has to establish ownership first — resolve a symlink with `readlink` and confirm the target points inside the tree the skill itself created (including that tree's former names) — and report anything else as `left untouched: <link> -> <target>` instead of deleting it. A broken link is usually temporary (a renamed repo, an unmounted disk) and the link is itself the record of where it pointed. This governs cleanup only; it does not apply where removal *is* the documented repair, as in `launchpad-fix` recreating the Spotlight store.
- **Paths.** Session transcripts and project memory live under `<harness-home>/projects/<slug>/`, where `<harness-home>` is `~/.claude` (Claude Code) or `~/.gemini/antigravity-cli` (Antigravity CLI) — use the first that exists. Skill state/config deliberately stays under `~/.claude/plugins/<name>/` (historical location; it is just a path, readable from any harness — no migration).
- **Names must be unique across the flat collection** and the directory name must equal the frontmatter `name`. Suites use prefixes (`tracker-*`, `work-*`).
- **Trigger phrases must discriminate, not just describe.** A `description` competes with every other description in the collection, so a phrase that reads naturally for two skills routes to whichever the model picks first — silently, and the user sees only the wrong result. This bites hardest between suites that share a domain: until 2026-08-11 `tracker-stop` advertised "end session", "I'm done" and "finished working", every one of which also means "the working day is over" (`work-end`), and `tracker-backfill` and `work-reconcile` both offered to fill in missing Toggl time with nothing saying which one covers the current session and which a past period. When two skills touch the same domain, give each description its own scope in its own words plus one clause naming its counterpart ("Not the end-of-day summary — that is `work-end`"). Drop any phrase you cannot assign to exactly one skill; an agent that has to ask beats one that guesses.
- **A mistyped command name cannot be fixed from a description.** Harnesses that expose skills as slash commands resolve the name locally: an unknown `/foo` is rejected before the turn starts and never reaches the model, so listing `"/foo"` among another skill's trigger phrases does nothing at all. Verified 2026-08-11 — a command the user reported typing by mistake "every now and then" appears in no session transcript. Fix a habitual typo where the name is resolved, in a personal command alias in the user's own config, never by adding an alias skill to this collection: every skill here costs description context in every session, for every user. And first establish which skill the user actually meant — an alias pointing at the plausible-but-wrong one converts a visible error into a silent wrong action.
- **Czech strings are functional, not accidental.** Trigger phrases in descriptions and user-facing message templates exist because the primary user works in Czech; skills phrase runtime output in the configured language. Do not "translate them away". Documentation prose, on the other hand, is English.
- **kodex** is a regular skill with an **always-on pointer**: one line in the user's instructions file makes agents load it before non-trivial work; `rules/kodex.md` is that line for Antigravity's rules mechanism. The English text in `SKILL.md` is canonical; the Czech original lives in `references/kodex-cs.md` — keep them in sync.
- Bundled assets (`scripts/`, `references/`, templates) belong inside the skill's directory and are referenced by paths relative to it.

## Dev loop

Edit in a working clone. Symlinked installs see changes immediately; copy installs refresh with `npx skills add . -g -y --all`. Verify discovery with `npx skills add . --list` (every skill must appear). When adding a skill, also add a row to the README table.

**Changelog.** `CHANGELOG.md` is date-grouped and scope-prefixed (skill name, or `repo` for collection-wide changes). Every `feat`/`fix` commit — and any other change that alters an installed skill's behavior or config contract — adds a line under today's date in the same push; typo/refactor/chore noise stays out. There are no repo-level versions or tags; the complete per-skill history remains `git log -- skills/<name>/`.

**Skill versions.** Some skills carry a frontmatter `version`, inherited from their Claude-plugin origin; it is optional, ignored outside Claude Code, and never added to a skill that lacks it. When a skill that has one changes behavior, bump it — patch for a fix, minor for a feature — and name the resulting version in parentheses at the end of its CHANGELOG line (`… (v1.6.1)`). Skills without the field get an unversioned line.
